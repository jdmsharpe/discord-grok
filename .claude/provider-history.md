# discord-grok - provider verification history

Evidence behind the rules in [CLAUDE.md](CLAUDE.md): probe results, dates, token counts, documentation quotes and how each rule came about. Each entry records what was true when it was written; where an entry and CLAUDE.md differ, CLAUDE.md describes the current code. Entries under "Provider notes" use the same bold title as the matching CLAUDE.md bullet.

When a change needs new evidence, add it here under the matching heading (or a new one) and keep the CLAUDE.md bullet to the rule, the constants to keep aligned and the guarding test.

## Provider notes

### Raw HTTP chat and SDK migration

- Raw Responses API behavior, retry/backoff handling, and file upload lifecycle now live primarily in `discord_grok.cogs.grok.client`. Chat uses raw HTTP rather than the SDK because xai-sdk does not yet expose a Responses API surface or `prompt_cache_key`; once both land, migrate `chat.py`/`client.py` onto the SDK like image/video already are (TTS is raw HTTP too). (Last checked xai-sdk 1.20.0, still the latest release, at the 2026-10-15 sweep: `Client` still has no `responses` attribute and `chat` has no `prompt_cache_key`, so the blocker remains. 1.20.0 only adds `last_frame_url` / `last_frame_file_id` / `keyframes` to `video.generate` / `start` / `prepare` (grok-imagine-video-1.5 only) and their protos — not wired; every kwarg the bot sends is unchanged. 1.18.0 added the `xhigh` reasoning effort and grok-4.6; 1.19.0 added `quality` to `image.sample` (both wired). Still unwired and available: `video.generate`'s `reference_audios`/`generate_audio` (1.19.0), Imagine file storage (`storage_options` + `public_url` on image/video results — could post the public URL to Discord instead of downloading and re-uploading bytes) and Files-API `file_id` inputs (1.16.0), and `compact_context()` for long-conversation compaction (1.15.0). Recheck on next minor bump. The 2026-09-22 sweep left xai-sdk at 1.19.0; grok-4.7 needed no SDK change because chat sends raw HTTP. `safety_identifier` on chat is on the SDK's unreleased main branch, not in 1.20.0.)

> 2026-11-06: rechecked on xai-sdk 1.21.0: `AsyncClient` still has no `responses` attribute and `chat.create` has no `prompt_cache_key`, so the blocker remains. `chat.create` now accepts `safety_identifier`; the bot sends that field over raw HTTP.

### Image and video cost

- Image/video cost: prefer `result.cost_usd` reported by xai-sdk 1.12+; fall back to bundled YAML pricing only when the SDK does not return a cost. Mock `cost_usd=None` in tests to exercise the YAML fallback path. TTS has no SDK cost surface — `calculate_tts_cost` always bills from the bundled YAML. `cost_usd` is the server's `cost_in_usd_ticks` (usage.proto: "Full price paid by the user for this request ... also used for image gen, video gen"), so it already includes xAI's flat **per-input-image surcharge** on edits / remixes and image-to-video — `pricePerInputImage` in the model table docs.x.ai embeds (1e-10 USD ticks): $0.01 on `grok-imagine-image-2.0`, `grok-imagine-image-quality` (+ its `-pro` alias), `grok-imagine-video-1.5-preview` and `grok-imagine-video-1.5-lite`, $0.002 on `grok-imagine-image` and `grok-imagine-video`. Only the YAML fallback needed it: each `image_generation` / `video_generation` row declares `per_input_image` (loaded into `IMAGE_INPUT_PRICING` / `VIDEO_INPUT_IMAGE_PRICING`; the `unknown_*` fallbacks are $0.01, the highest published rate, so an unknown model is not under-billed), and `calculate_image_cost(..., input_images=N)` / `calculate_video_cost(..., input_images=N)` add it; `image.py` passes 1 when editing, `video.py` when an attachment is supplied for image-to-video. Pinned by `test_bundled_yaml_loads_input_image_surcharges` (`tests/test_config_pricing.py`), the `*_adds_input_image_surcharge*` cases in `tests/test_util.py`, and the two `*_yaml_fallback_adds_input_image_surcharge` command tests.

### Chat cost

- **Chat cost (v1.10.0):** `extract_usage` (`responses.py`) reads `usage.cost_in_usd_ticks` (1e-10 USD; present on every Responses API reply probed 2026-09-15, and equal to the catalog computation to the tick) into `cost_usd`, and both chat paths in `chat.py` bill that figure when present, falling back to `calculate_cost` + `calculate_tool_cost`. Tool counts come from `extract_tool_usage`: current responses report them under `usage.server_side_tool_usage_details` (`x_search_calls`, `web_search_calls`, `code_interpreter_calls`, `file_search_calls`, `mcp_calls`, `document_search_calls`, `image_generation_calls` → `SERVER_SIDE_TOOL_*` keys), not the top-level `server_side_tool_usage` map the bot read before (still honoured when present) — so until v1.10.0 tool calls were unbilled by the catalog path and missing from the embed's tool line. The cost line shows tools only as call counts (labels in `TOOL_USAGE_DETAIL_LABELS`, `tooling.py`); their charges are inside the request cost it shows. xAI's `output_tokens` includes `reasoning_tokens` (docs.x.ai says otherwise): one request per chat model (grok-4.7, 4.6, 4.5, 4.3, 4.20, 4.20-multi-agent) on 2026-09-22 returned `total_tokens` = input + output and a `cost_in_usd_ticks` equal to the catalog cost of `output_tokens` alone. So `calculate_cost` bills `output_tokens` once (it billed `output_tokens + reasoning_tokens` before v1.11.1, which over-billed the catalog fallback), and `append_pricing_embed` shows `output_tokens` as the `out` count with `reasoning_tokens` in parentheses. Since 2026-09-21 12:00 PT X Search bills $5 per 1,000 posts and $10 per 1,000 user profiles fetched (pricing page + X Search tool page), so the `SERVER_SIDE_TOOL_X_SEARCH` per-call row is only a fallback estimate and only the reported cost is exact. Pinned by `test_extract_usage_reports_the_server_cost`, `test_extract_tool_usage_reads_usage_details` and `test_extract_tool_usage_keeps_the_legacy_top_level_map` in `tests/test_grok_responses.py`.

> 2026-11-06: the three tests named above no longer exist; `extract_usage` / `extract_tool_usage` are covered through `tests/test_grok_chat.py::test_chat_cost_line_shows_the_reported_cost_added_to_the_daily_total` and `tests/test_grok_responses.py::test_extract_usage_with_details`.

### grok-4.7

- **grok-4.7 (default since the 2026-09-22 sweep):** facts verified 2026-09-22 against docs.x.ai (September release notes; the us-east-1 row of the models-page JSON) and a live request built with `build_responses_payload` to `api.x.ai/v1/responses`. Pricing equals grok-4.6's: $2.00 input / $0.50 cached / $6.00 output per MTok, and every token at $4.00 / $1.00 / $12.00 once a prompt reaches 200k tokens, so the catalog entry uses the `grok_4_6` class. 500k context; text and image input. `reasoning_effort` accepts `low`, `medium`, `high` and `xhigh`; `none` returns 400 "This model does not support `reasoning_effort` value `none`." (reasoning cannot be disabled), and a request without an effort still reasons (xAI documents `high` as the default). `temperature` and `presence_penalty` both returned 200. The catalog still gates penalties exactly as on grok-4.6 (no `supports_penalties` capability, so `chat.py` rejects `frequency_penalty` / `presence_penalty` before the request): a 200 does not show that the penalty changes the output, and `frequency_penalty` was not tried. Enabling them would also need the "Non-reasoning models only" option descriptions and `test_penalty_supported_models_are_non_reasoning` changed. `temperature` is not gated for any model. Every grok-4.7 response carries `reasoning.encrypted_content` even when `include` does not request it; `extract_response_text` reads only `summary_text` parts, so the bot ignores it. `usage.cost_in_usd_ticks` is present on every response. grok-4.6 stays selectable. Pinned by `test_default_chat_model_is_grok_4_7` and `test_grok_4_7_entry_matches_its_published_spec` (`tests/test_grok_commands.py`).

### Reasoning efforts

- **Reasoning efforts (re-verified 2026-10-08):** docs.x.ai model pages list `low`, `medium`, `high`, `xhigh` for grok-4.5, 4.6 and 4.7, and `none`, `low`, `medium`, `high`, `xhigh` for grok-4.3 (documented default `low`; the others default to `high`). A request built with `build_responses_payload` returned 200 with `reasoning.effort` echoed `xhigh` on both grok-4.5 and grok-4.3, and an invalid value (`max`) returned 400 "Invalid reasoning effort.", so xAI validates the value rather than mapping unknown efforts to `high` (an earlier comment claimed models without `xhigh` silently treat it as `high`; that is wrong). `xhigh` is therefore in the `reasoning_efforts` set of all four effort models. Pinned by `test_xhigh_is_offered_on_every_effort_model` (`tests/test_util.py`) and `test_chat_passes_xhigh_effort` (`tests/test_grok_chat.py`).

### Multi-agent agent count

- **Multi-agent agent count (fixed 2026-10-15):** the `/grok chat` `agent_count` option on `grok-4.20-multi-agent` is sent as `reasoning: {"effort": ...}` (`MULTI_AGENT_EFFORT_BY_AGENT_COUNT` in `client.py`: 4 → `medium`, 16 → `high`). The Responses API has no `agent_count` field: the Configuration table on [docs.x.ai's multi-agent page](https://docs.x.ai/developers/model-capabilities/text/multi-agent) lists `agent_count` for the xAI SDK only and `reasoning.effort` for the REST API (`low`/`medium` → 4 agents, `high`/`xhigh` → 16). Until this fix the bot sent a top-level `agent_count`, which the server ignored, so "16 Agents" ran 4. Probes on 2026-10-15: `agent_count: "abc"` returned 200 (a field the server reads returns 422 on a wrong type), `agent_count: 16` used the same 2.7k–8.3k input tokens as sending nothing, and nested `reasoning.effort` `high`/`xhigh` used 22k–40k. A 16-agent request now costs about 4–6x a 4-agent one (billed from `cost_in_usd_ticks`). The multi-agent model accepts any effort string without validation and always echoes `medium`, so the echo does not show which setting ran. `reasoning_effort` stays rejected on the multi-agent model (its catalog entry has no `reasoning_efforts`). Pinned by `test_chat_sends_agent_count_as_reasoning_effort_for_multi_agent` and `test_follow_up_sends_agent_count_as_reasoning_effort` (`tests/test_grok_chat.py`).

### `safety_identifier`

- **`safety_identifier` (added 2026-10-08, John: "as long as information about user ID is removed"):** both chat paths in `chat.py` pass `build_safety_identifier(<author id>)` (`safety.py`) to `build_responses_payload`, which sets the top-level `safety_identifier` field of the POST /v1/responses body; `image.py` sends the same value as `user=` on `image.sample` / `image.sample_batch` (generation and editing; editing is single-image only). The value is `hmac.new(key, str(discord_user_id), sha256).hexdigest()` (64 hex chars, not truncated). Key: `SAFETY_IDENTIFIER_SECRET` (stripped) as UTF-8 bytes when set, else `HMAC-SHA256(BOT_TOKEN, b"safety-identifier-v1")`; computed once at import into `SAFETY_IDENTIFIER_KEY`. With neither set no identifier is sent (never an unkeyed hash: Discord user IDs are enumerable). This is the construction shared with discord-claude, discord-openai and discord-openrouter (same env var, same label, same output); change all four together. Never key it with `XAI_API_KEY`: xAI holds that key and could rebuild the mapping; `validate_required_config()` rejects a `SAFETY_IDENTIFIER_SECRET` equal to `XAI_API_KEY`. Rotating `BOT_TOKEN` without the secret changes every user's value. Nothing logs the identifier or the key.
  - Docs read 2026-10-08: [Responses API reference](https://docs.x.ai/developers/rest-api-reference/inference/responses) — `safety_identifier` (string | null), top-level request field, "hash your internal user id or username rather than sending an email or name"; the response object also has a `safety_identifier` field. [Security FAQ](https://docs.x.ai/developers/faq/security#how-do-i-identify-which-of-my-end-users-caused-a-policy-violation) — "SpaceXAI does not validate the format" (no length or character limit documented); accepted on Chat Completions, the Responses API (incl. streaming and WebSocket mode), deferred chat completions, the Batch API and gRPC `GetCompletionsRequest`; the legacy `user` field is still accepted. [Release notes](https://docs.x.ai/developers/release-notes), September. [Voice reference](https://docs.x.ai/developers/rest-api-reference/inference/voice): POST /v1/tts lists neither `safety_identifier` nor `user`. Images and Videos references list only the legacy `user` field ("A unique identifier representing your end-user").
  - Which requests carry it: POST /v1/responses (raw HTTP) as `safety_identifier`; `image.sample` / `image.sample_batch` (xai-sdk 1.20.0, gRPC `GenerateImageRequest.user`) as `user`. Not sent: POST /v1/tts (documents neither field); `video.generate` (xai-sdk 1.20.0 has neither a `safety_identifier` nor a `user` parameter, and the v5/v6 video protos have no `user` field); `files.upload` / `files.delete` (not inference requests). xai-sdk 1.20.0 has no `safety_identifier` parameter anywhere (the chat field is on the SDK's unreleased main branch).
  - SDK telemetry: the async `image.sample` / `sample_batch` the bot calls build their span attributes with `xai_sdk.image._make_span_request_attributes`, which copies a non-empty `request.user` into the `user_id` span attribute unless `XAI_SDK_DISABLE_SENSITIVE_TELEMETRY_ATTRIBUTES` is `1`/`true` (it also records the prompt). The bot creates no `xai_sdk.telemetry.Telemetry` and installs no OpenTelemetry tracer provider, so the spans are non-recording and the attribute goes nowhere; if tracing is ever enabled, that attribute holds the keyed identifier, not the Discord user ID. Checked in the installed xai-sdk 1.20.0 source on 2026-10-08.
  - Live 2026-10-08 (chat only; payload from `build_responses_payload` + `build_user_message`, grok-4.3, `reasoning_effort` none): a 64-hex value returned 200 ($0.000107); the response's `safety_identifier` key is present but `null` (not echoed back). An integer value returned 422 "safety_identifier: invalid type: integer `12345`, expected a string", so the server parses the field rather than dropping it. No over-limit probe: no limit is documented. The image `user` field was not probed: it is in the xai-sdk 1.20.0 signature and proto and in the docs.x.ai Images reference.
  - Pinned by `tests/test_grok_safety.py` (determinism, per-user and per-secret difference, the shared `b"safety-identifier-v1"` label, two literal 64-hex vectors that discord-claude, discord-openai and discord-openrouter must also produce (`BOT_TOKEN=tok` with no secret, and secret `shared-secret`, both for user 111222333; `test_fixed_vectors_shared_with_sibling_bots`), not the raw or unkeyed-hashed ID, present on `/grok chat` and follow-up payloads and as `user` on image generate (`sample` and `sample_batch`) and edit kwargs, every image kwarg the bot sends being a parameter of the installed `xai_sdk.aio.image.Client` method (the fixture's image client is an unspecced mock), the raw ID in none of them, `user` omitted without a key, absent from video SDK kwargs and the TTS payload, absent from logs; `test_module_key_is_read_from_the_environment` runs fresh copies of `auth.py` and `safety.py` with the secret set, with only `BOT_TOKEN`, and with neither) and `test_safety_identifier_secret_is_optional_and_stripped` / `test_validate_required_config_rejects_the_api_key_as_safety_secret` (`tests/test_config_auth.py`).

> 2026-11-06: xai-sdk 1.21.0 adds `safety_identifier` to `chat.create` only; `image.sample` still takes `user`, and `video.generate` takes neither.

### Resolution-based media pricing

- Grok Imagine bills per **output resolution**, so `image_generation` / `video_generation` rows in `pricing.yaml` map resolution → rate and `calculate_image_cost` / `calculate_video_cost` take the requested resolution. `grok-imagine-image-2.0` bills on resolution AND quality; its rows are keyed `"<resolution>/<quality>"` so the normalized map stays flat, and `calculate_image_cost` bills the dearest tier for a resolution when no quality is supplied. 1080p is priced only for `grok-imagine-video-1.5-preview` and `grok-imagine-video-1.5-lite`, so `_validate_video_resolution` (`video.py`) rejects it on other models rather than letting it reach the unknown-model fallback. A scalar rate is still accepted and bills flat. When a caller passes no resolution, the tier assumed is `DEFAULT_IMAGE_RESOLUTION` / `DEFAULT_VIDEO_RESOLUTION` in `tooling.py`, which must track the `/grok-media` option defaults.

### Stickers are sent as text

- **Stickers are sent as text (v1.13.1).** A Discord sticker arrives with empty `content` and no `attachments`; `handle_new_message_in_conversation` (`chat.py`) sends each sticker in `message.stickers` as a `[Sticker: <name>]` line after the message text, built by `text_with_stickers` in `stickers.py`, which is byte-identical in the five AI bots (change all five together). The sticker image is not sent. A follow-up with nothing to send (no text, no sticker, no attachment that yields content) is ignored and the conversation stays open. Before, discord-openai, discord-gemini and discord-claude sent an empty turn, got a 400, and the error path removed the conversation; discord-grok and discord-openrouter dropped a sticker-only message without a reply. Pinned by `tests/test_stickers.py` and the sticker follow-up tests in `tests/test_grok_chat.py`.

### Pricing

- **Pricing** is loaded from `src/discord_grok/config/pricing.yaml` by `config/pricing.py` at import time. Chat pricing uses a class indirection (`MODEL_PRICING_CLASSES`) joined to `CHAT_MODEL_CATALOG` in `command_options.py`. Override the YAML via `XAI_PRICING_PATH`. **[docs.x.ai](https://docs.x.ai/docs/models) is canonical**; [genai-prices/x_ai.yml](https://github.com/pydantic/genai-prices/blob/main/prices/providers/x_ai.yml) is a secondary cross-reference only and is known stale for xAI — on 2026-07-24 it still carried grok-4.5's retired $0.50/M cached rate, so trusting it would have masked that drift. Verify prices against docs.x.ai first. In the model JSON docs.x.ai embeds, only the us-east-1 rows carry the base price; us-central-1 rows include a 1.1x regional premium. The 2026-10-08 re-diff found every `pricing.yaml` row matching docs.x.ai except `SERVER_SIDE_TOOL_ATTACHMENT_SEARCH`, which dropped from $10 to $5 per 1,000 calls (pricing.md "File Attachments | `attachment_search` | ... | $5"; the 2026-09-18 copy said $10) and was corrected. That row is a catalog-fallback estimate only: the reported `cost_in_usd_ticks` wins when present.
